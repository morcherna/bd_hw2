
## 1. Вводные данные

В качестве источника использован набор **Road Safety Data – Collisions – 2025**, опубликованный UK Department for Transport.

**Потребитель данных:** аналитик по безопасности дорожного движения.

Основной аналитический вопрос:

Как изменяется количество ДТП и пострадавших в зависимости от дня недели и типа дороги?

Дополнительный вопрос:

Какие типы дорог характеризуются наибольшим количеством серьёзных ДТП в рассматриваемом периоде?

## 3. Модель DWH

### 3.1. Зерно факта

Зерном таблицы `fct_collisions` является:

- одна зарегистрированная авария (collision), идентифицируемая уникальным `collision_index`.

Таким образом, одна строка факта соответствует одному ДТП.

---

### 3.2. Таблицы

#### Raw

`raw.raw_collisions`

Содержит исходные записи контрольного среза после загрузки CSV в PostgreSQL.

#### Staging

`dbt_staging.stg_collisions`

Staging-слой приводит исходные данные к типам и оставляет только требуемый контрольный период:

```text
2025-01-01 <= date < 2025-02-01
```

#### DWH

`dbt_dwh.dim_date`

Измерение даты:

- `date_key`;
- `full_date`;
- `day_of_week`;
- `day_name`;
- `month`;
- `year`.

`dbt_dwh.dim_road`

Измерение дороги:

- `road_key`;
- `first_road_class`;
- `road_type`;
- `road_type_label`;
- `speed_limit`;
- `urban_or_rural_area`.

`dbt_dwh.fct_collisions`

Факт:

- `collision_index`;
- `date_key`;
- `road_key`;
- `collision_severity`;
- `collision_severity_label`;
- `number_of_vehicles`;
- `number_of_casualties`.

#### Mart

`dbt_mart.mart_daily_road`

Агрегированная витрина с зерном:

> дата × день недели × тип дороги.

Витрина содержит:

- `full_date`;
- `day_of_week`;
- `day_name`;
- `road_type`;
- `road_type_label`;
- `collisions_count`;
- `casualties_count`;
- `serious_collisions_count`;
- `vehicles_count`.

## 4. Почему выбрана такая модель

Измерения даты и дороги вынесены отдельно, поскольку они используются для аналитических разрезов, а числовые показатели ДТП находятся в таблице фактов.

Для `dim_date` используется ключ в формате `YYYYMMDD`.

Для `dim_road` используется суррогатный `road_key`, так как комбинация атрибутов дороги является составным естественным идентификатором.

История измерений в рамках данной работы не моделируется как SCD. Контрольный срез относится к фиксированному периоду января 2025 года, а задача заключается в воспроизводимой аналитике этого среза. Поэтому достаточно текущего состояния измерений без версионирования изменений.

## 8. Контроль качества данных

В dbt реализованы следующие проверки:

1. `collision_index` не должен быть `NULL`;
2. `collision_index` должен быть уникальным;
3. `collision_date` не должен быть `NULL`;
4. `road_type_label` не должен быть `NULL`;
5. `date_key` должен быть уникальным;
6. `road_key` должен быть уникальным;
7. `fct_collisions.date_key` должен существовать в `dim_date`;
8. `fct_collisions.road_key` должен существовать в `dim_road`;
9. `collision_severity_label` должен принимать только допустимые значения:
   - `Fatal`;
   - `Serious`;
   - `Slight`;
10. количество пострадавших не может быть отрицательным.

Последнее правило реализовано отдельным SQL-тестом:

```sql
select
    collision_index,
    number_of_casualties
from {{ ref('fct_collisions') }}
where number_of_casualties < 0
```

Тест считается успешным, если запрос возвращает ноль строк.

## 10. Четыре диагностических сценария

Для проверки DQ были независимо рассмотрены четыре типа ошибок. Перед каждым сценарием данные возвращались к чистому контрольному состоянию.

### 10.1. Дубликат ключа

**Изменение:**

В `raw.raw_collisions` добавлялась копия существующей строки.

Получалось:

```text
raw rows = 8164
distinct collision_index = 8163
```

**Ожидание:**

Тест уникальности `collision_index` должен завершиться ошибкой.

**Наблюдение:**

Тест:

```text
unique_stg_collisions_collision_index
```

завершился с ошибкой.

Получен один нарушающий строковый результат.

**Причина:**

В raw-слое появился второй экземпляр того же `collision_index`, поэтому staging-модель нарушила ограничение уникальности.

### 10.2. NULL

**Изменение:**

Для одной записи значение:

```text
road_type_label
```

было заменено на `NULL`.

**Ожидание:**

Тест `not_null` должен обнаружить ошибку.

**Наблюдение:**

Получена ошибка:

```text
not_null_stg_collisions_road_type_label
```

Остальные зависимые модели после ошибки не публиковались.

**Причина:**

Поле является обязательным для аналитического разреза по типу дороги.

### 10.3. Недопустимое значение

**Изменение:**

Для одной записи:

```text
collision_severity_label = 'Unknown'
```

**Ожидание:**

Тест `accepted_values` должен обнаружить значение, отсутствующее в разрешённом наборе.

Разрешены только:

```text
Fatal
Serious
Slight
```

**Наблюдение:**

Тест:

```text
accepted_values_fct_collisions_collision_severity_label__Fatal__Serious__Slight
```

завершился ошибкой.

**Причина:**

Значение не соответствует справочнику допустимых категорий.

### 10.4. Нарушение бизнес-правила

**Изменение:**

Для одной записи:

```text
number_of_casualties = -1
```

**Ожидание:**

SQL-тест `business_rule_casualties` должен вернуть нарушающую запись.

**Наблюдение:**

Тест:

```text
business_rule_casualties
```

завершился ошибкой.

**Причина:**

Количество пострадавших не может быть отрицательным.

## 11. Изоляция публикации при ошибке

Для предотвращения публикации некорректного результата используются два слоя:

```text
candidate.mart_daily_road
published.mart_daily_road
```

Публикация в `published` выполняется отдельным шагом только после успешного `dbt test`.

Поэтому при DQ-ошибке новая версия витрины не заменяет последнюю корректно опубликованную версию.

До возникновения ошибки опубликованная витрина содержала:

```text

serious_collisions = 1867

```

После намеренного DQ-нарушения эти значения в `published.mart_daily_road` сохранялись без изменений.

## 14. Воспроизводимость

Пайплайн использует фиксированный контрольный срез:

```text
2025-01-01 — 2025-01-31
```

Дата запуска Airflow не используется как дата события.

При повторном выполнении loader сначала очищает raw-слой и затем загружает тот же контрольный файл.

Результат определяется входным набором данных, SQL-моделями и конфигурацией пайплайна, а не моментом запуска.

## 15. Ограничения решения

1. Контрольный срез содержит только январь 2025 года, поэтому результат нельзя интерпретировать как статистику всего 2025 года.
2. Тест уникальности подтверждает отсутствие дубликатов ключа, но сам по себе не доказывает полноту исходного набора.
3. Историческое версионирование измерений SCD в данной работе не реализовано, поскольку задача ограничена фиксированным контрольным периодом.
4. Raw-слой содержит только поля, необходимые для построения выбранной аналитической витрины.
5. PostgreSQL, Airflow и dbt запускаются локально в Docker Compose, поэтому решение не предназначено для оценки производительности промышленного кластера.
